## Incident INC-2026-0001 — Confirmed multi-stage intrusion and credential compromise

| Field | Value |
|---|---|
| **Incident** | `INC-2026-0001` |
| **Title** | Multi-stage attack from `203.0.113.66` |
| **Severity** | CRITICAL |
| **Category** | intrusion |
| **Status** | contained → resolved |
| **Opened / detected** | first alert `NET-PORTSCAN-001`, chain window start |
| **Affected host** | `soc-01` (`192.0.2.10`) |
| **Source** | `203.0.113.66` (single source for all 13 alerts) |
| **Chain** | `chain_id = 1` (all 13 alerts grouped) |
| **Analyst** | admin |

### Summary

A single external source (`203.0.113.66`) conducted a full intrusion sequence
against `soc-01` in under 5 minutes: a port scan, then web-application
exploitation against DVWA, web login brute force, a successful SSH brute force,
and — at the end — host-originated traffic consistent with command-and-control
and DNS exfiltration. The platform raised all 13 rules across the sequence,
correlated them into **one chain** from one source, and the analyst promoted that
chain to this incident and contained the source with a real firewall block.

The successful SSH login (`SSH-SUCCESS-001`) is the critical fact: the account
`admin` must be treated as **compromised** — a failed brute force is an attempt,
this was a success.

### Timeline (relative to detection start)

| Δ | Alert | Severity | Evidence |
|---|---|---|---|
| 0:00 | `NET-PORTSCAN-001` | MEDIUM | 24 distinct destination ports, one source, 60 s |
| 0:05 | `IDS-SIG-001` | MEDIUM | IDS signature 9000003 (SYN-flood shape) |
| 0:10 | `SSH-BF-001` | HIGH | 12 failed `ssh_login` for `admin`, 5-minute window |
| 0:15 | `WEB-BF-001` | HIGH | 22 `POST /login` `401` responses, 120 s |
| 0:20 | `WEB-SQLI-001` | HIGH | `id=1' OR '1'='1` in decoded URI (UA `sqlmap/1.8`) |
| 0:21 | `WEB-XSS-001` | MEDIUM | `<script>alert(1)</script>` in decoded URI |
| 0:22 | `WEB-CMD-001` | HIGH | `ip=127.0.0.1; id` command-injection on the exec page |
| 0:23 | `WEB-LFI-001` | HIGH | `page=../../../../etc/passwd` traversal |
| 0:25 | `WEB-SCAN-001` | MEDIUM | `Nikto/2.5.0` User-Agent |
| 0:27 | `WEB-FLOOD-001` | MEDIUM | 305 status-`301` GETs from one source, 60 s |
| 0:30 | `SSH-SUCCESS-001` | **CRITICAL** | `Accepted password for admin` from the brute-forcing source |
| 0:40 | `NET-OUTBOUND-001` | MEDIUM | host opened TCP/4444 to `203.0.113.9` (not allow-listed) |
| 0:45 | `DNS-ANOMALY-001` | LOW | over-long DNS label `aGVsbG8td29ybGQ.exfil.example.net` |

### Analysis

1. **Reconnaissance.** The port scan and the IDS signature establish intent and a
   target list; on their own they are attention-worthy, not alarming.
2. **Exploitation attempt.** Four web rules fire almost simultaneously. The
   tooling fingerprint (`sqlmap`, `Nikto`) says this is automated, not a user
   mistyping a URL.
3. **Credential attack → success.** The brute force is followed by an
   `Accepted`. This is the pivot from "attempted" to "compromised".
4. **Post-compromise.** Seven minutes later the host itself opens an unexpected
   outbound connection and queries over-long DNS labels — consistent with
   beaconing / exfiltration from the compromised account. Rules 12 and 13 exist
   precisely to catch what the host does *after* it is owned.

Correlation matters here: 13 alerts from **one** source inside the window are one
story. The risk of treating them as 13 separate tickets is that nobody sees the
kill chain.

### Response actions taken

| Action | Target | Result | Status |
|---|---|---|---|
| `block IP` | `203.0.113.66` | `blocked 203.0.113.66 for 3600s` (`nft list set inet filter blocklist`) | executed |
| `disable account` | `admin` | password reset + `authorized_keys` rotated | executed |
| Promote chain to incident | `chain_id = 1` | `INC-2026-0001` opened, CRITICAL | done |
| Investigation notes | — | two notes recorded (chain summary; remediation advice) | — |

### Verification

- `nft list set inet filter blocklist` shows `203.0.113.66`.
- A subsequent SSH attempt from the source times out (SG/nftables drop).
- Status history recorded `open → investigating`; the incident is contained and
  then resolved by the on-call lead.

### Recommendations

1. **Rotate credentials and disable SSH password authentication** for
   internet-facing hosts (keys only); the compromised account's secrets are
   burned regardless of the block.
2. **Investigate the outbound beacon** (4444) and the DNS query target — if the
   host is confirmed compromised, rebuild from the clean-baseline AMI rather than
   cleaning in place.
3. **Tune on correlation, not single alerts.** Keep the chain window; alert on
   `SSH-SUCCESS-001` after a brute-force alert as CRITICAL, which is already the
   behaviour here — verify it stays that way.
4. **Rate-limit SSH at the host** (e.g. `MaxStartups`, key-only) so a brute force
   cannot succeed at all, independent of the SOC.

### Lessons / rule confirmation

All 13 rules fired from a single live sequence and correlated into one chain —
the end-to-end loop (collect → detect → correlate → respond) works on real
traffic. No rule needed threshold tuning for this run.

## Incident INC-2026-0002 — Benign source, triaged as false positive

| Field | Value |
|---|---|
| **Incident** | `INC-2026-0002` |
| **Title** | Sub-threshold activity from second (allow-listed) source |
| **Severity** | LOW |
| **Category** | policy / benign |
| **Status** | closed — FALSE POSITIVE |
| **Source** | second benign source (phone hotspot), allow-listed |
| **Affected host** | `soc-01` |

### Summary

During the false-positive control segment of the demo, a second, controlled
source (the operator's phone hotspot — see
[`../testing/second-source-ip.md`](../testing/second-source-ip.md)) loaded the
DVWA landing page a handful of times. The source is *not* the attacker and the
traffic is normal use.

The platform handled it correctly: the volume stayed **below every threshold**, so
no alert was raised. One stray `WEB-SCAN-001`-like hit — a single request whose
User-Agent matched a scanner token (a browser extension in this case) — was the
only thing to appear, and it was **not** enough on its own to be alarming.

### What the analyst did

1. Confirmed the source IP was the operator's hotspot, not an unknown host.
2. Confirmed the request volume was a single request (count 1), below the
   scanner rule's intent and with no exploitation payload.
3. Marked the alert **FALSE POSITIVE** with a note; the source stays
   allow-listed so its benign traffic does not re-alert.
4. Closed the incident.

### False-positive control result

| Source | Traffic | Alerts raised | Verdict |
|---|---|---|---|
| `203.0.113.66` (attacker) | scan + exploits + brute force | 13, one chain | true positive — incident 0001 |
| hotspot (benign) | a few `GET /` | 0–1 (sub-threshold) | false positive, suppressed |

This is the point of the segment: **the same kind of HTTP request** is normal from
one source and exploitation-shaped from another; the rules key on **payload and
volume**, not merely on traffic existing, which is what keeps false positives
low.

### Notes

- If a browser ever produces a real scanner-UA alert (extensions do), prefer
  tuning the User-Agent allow-list for that UA over suppressing `WEB-SCAN-001`,
  so genuine scanners still alert.
- Record the hotspot IP in the session log — mobile IPs rotate and are NATed.
